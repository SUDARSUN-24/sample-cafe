# How it works

This explains every file in plain language, and why it was built this way. Read it top to bottom
once and you should be able to explain the whole project in an interview.

---

## 1. The big idea in one paragraph

All shop details live in **one data file, `site/config.js`**. A set of **template functions**
(`site/js/render.js`) turns that data into HTML. Those same templates run in two places:

1. **On your computer, before you deploy.** `node tools/bake.mjs` runs the templates and writes the
   finished HTML into `index.html`. This is called **baking**. Google, LINE link previews and
   visitors with JavaScript turned off all get a complete page straight away.
2. **In the browser, as a live preview.** If you edit `config.js` and forget to bake, `main.js`
   notices and rebuilds the page from config in the browser. You can see the change straight away,
   and the console reminds you to bake.

There's one source of truth (config) and one set of templates, so the two copies can never drift
apart. There's still no build step for deploying: the baked `site` folder is just static files.

```
config.js ──┐
            ├──► render.js templates ──► bake.mjs (Node) ──► index.html  (what you deploy)
manifest.js ┘                       └──► main.js (browser) ──► live preview if config changed
(image list)
```

### How the page knows it is out of date

`render.js` has a `buildId()` function. It hashes config + the image list into a short code
(FNV-1a hash, e.g. `djpxp0`). The bake writes that code into `<html data-build="djpxp0">`. When the
page loads, `main.js` hashes the current config again. Same code: do nothing, the HTML is already
correct. Different code: re-render.

## 2. What happens when someone opens the page

1. **HTML arrives** with all content already in it (baked). The browser starts drawing at once.
2. **`boot.js`** (tiny, in `<head>`) runs before anything is drawn:
   - adds the `js` class to `<html>`, so the CSS knows it can hide elements for their entrance
     animations (without JS they are never hidden);
   - reads the saved language (`localStorage "shop-lang"`) and sets `<html lang>`, so there is no
     flash of the wrong language;
   - starts a 3-second safety timer: if `main.js` never loads, show everything anyway.
3. **CSS** loads: `styles.css` (design) and `shop.generated.css` (this shop's colors and photo
   placeholders).
4. **Fonts and hero photo** were already requested early by `<link rel="preload">` tags.
5. **Deferred scripts** run in order once the HTML is parsed: `config.js` → `manifest.js` →
   `render.js` → `hours.js` → `main.js`. "Deferred" means they never block the first paint.
6. **`main.js`** wires up everything interactive (section 5).

## 3. Files in `site/` (what gets deployed)

| File | What it is, in plain words |
| --- | --- |
| `config.js` | **The only file you edit per shop.** Name, contact, map pin, directions, hours, photos and their alt text, menu, story, reviews, theme, SEO text. Sets `window.SHOP_CONFIG`. Places to change are marked `CHANGE-ME`. |
| `index.html` | The page skeleton: `<head>`, the SVG icon sprite (all icons drawn once, reused with `<use>`), and empty "slots" between `<!--render:hero-->` … `<!--/render:hero-->` markers that the bake fills. |
| `404.html` | "Page not found", generated by the bake, so it matches the shop's name and colors. Netlify shows a file with this exact name for unknown URLs automatically. |
| `netlify.toml` | Tells Netlify which **HTTP headers** to send: security rules (section 7) and how long browsers may cache each file type. |
| `vercel.json`, `.vercelignore` | The same headers in Vercel's format, plus the list of tool files Vercel shouldn't upload. If you change one header file, change the other too. |
| `robots.txt`, `sitemap.xml` | Tell search engines they may index the site, and where the page is. Generated with the real URL. |
| `site.webmanifest`, `favicon.ico`, `icon-*.png`, `apple-touch-icon.png` | Name and icons used when the site is saved to a phone's home screen or shown in a browser tab. |
| `js/boot.js` | Runs first, before drawing. See step 2 above. Deliberately about 15 lines. |
| `js/render.js` | **The templates.** One function per section (`hero`, `find`, `menu`, `gallery`…) that takes config and returns an HTML string. Also builds the `<head>` tags (SEO, link previews, JSON-LD), the theme CSS and the QR code SVG. It works the same in Node and in the browser. |
| `js/hours.js` | Works out "Open now / Closes at 18:00 / Opens Thursday 07:30" in **Bangkok time**, whatever time zone the visitor's phone is in. Plain logic, no page code, so it has unit tests. |
| `js/main.js` | **Everything interactive.** Language toggle, live open status, header, parallax, scroll reveals, menu tabs, lightbox, reviews carousel, map-on-tap, copy address, mobile menu, QR. |
| `js/vendor/qrcode.js` | A small, well-known MIT-licensed QR code library, self-hosted. Loaded only when the QR is about to scroll into view. |
| `css/styles.css` | The whole design, in 14 numbered sections (tokens → base → header → … → reduced motion). Colors are CSS variables, never hard-coded. |
| `css/shop.generated.css` | Written by the bake: this theme's color variables, and a tiny blurred version of each photo used as its placeholder. Lives in a file, not inline, because of the security policy (section 7). |
| `css/404.css` | Styles for the 404 page (the steaming cup). |
| `assets/fonts/` | The two typefaces as small WOFF2 files, plus their licences. See section 8. |
| `assets/img/` | Every photo in several sizes and formats, with a short code in the name (`latte.3f9a1c-640.avif`). `manifest.js` lists them for the templates. |

## 4. Ideas worth understanding

### Two languages without two pages
Every piece of text is output in both languages:

```html
<span lang="th" data-l="th">เปิดอยู่</span><span lang="en" data-l="en">Open now</span>
```

CSS hides whichever one doesn't match `<html lang>`. Switching language changes one attribute.
Nothing is re-downloaded, the switch is instant, and search engines see both languages. The `lang`
attribute on each span also tells screen readers which voice to use.

Attributes such as `alt` and `aria-label` can't hold two spans, so they are stored as
`data-alt-th` / `data-alt-en`, and `main.js` copies the right one in when the language changes.

### Thai typography
Thai has tone marks and vowels stacked above and below letters, so Thai text needs more line
height than English (body 1.75 vs 1.6, headings 1.3 vs 1.02). The CSS switches these values with
the language. Otherwise the marks of one line touch the next, or are clipped.

### Opening hours (`hours.js`)
- It asks `Intl.DateTimeFormat` for the current day and time **in Asia/Bangkok**, so a tourist
  whose phone is set to London still sees the right status.
- It handles **overnight** hours (e.g. 18:00–02:00: still open at 01:00 on the next day), **split**
  days (e.g. 07:00–11:00 and 17:00–22:00), one-off **closed dates** (holidays) and a weekly
  closed day.
- "Closing soon" appears in the last hour.
- `main.js` refreshes the status every minute and when the phone is unlocked (`visibilitychange`).
- The 11 tests are in `tools/tests/hours.test.mjs`.

### "How to find us" comes first
Many small Bangkok shops are hard to find (inside a petrol station, up a soi, on a second floor).
The Find-us section gives numbered steps with landmarks a first-timer can see, a step photo,
transit and parking notes, and the hours with **today** highlighted. The map isn't loaded until
the visitor taps it. A map iframe is heavy (about 1 MB) and would also send data to the map company
for every visitor.

### Reviews
The reviews are honestly labelled as sample text while `isSample` is `true`. They are **left out of
Google's structured data** on purpose: Google treats a business marking up its own reviews as
self-serving.

## 5. Motion and interaction (`main.js` + `styles.css`)

Rule followed everywhere: **only animate `transform` and `opacity`.** The browser can do those on
the graphics card without recalculating layout, so they stay at 60 fps and never shift content
(no layout shift, which Google measures as CLS).

| Feature | How it works |
| --- | --- |
| Page-load and scroll reveals | An `IntersectionObserver` watches elements with the class `reveal`. When one scrolls into view it gets the class `is-in`, and CSS fades and slides it up. Children of `data-stagger` get growing delays. Each element is watched only once. |
| Hero parallax | On scroll, the hero photo layer moves at 18% of the scroll speed. It is done in `requestAnimationFrame` (once per frame), only while the hero is on screen. The photo layer is 18% taller so no gap shows. |
| Sticky header | An invisible marker sits at the top of the page. When it scrolls away, the header gets `is-scrolled`: its background shrinks (`scaleY`), the content moves up (`translateY`) and a blur backdrop appears. It never changes `height`, so nothing below jumps. |
| Mobile action bar | Call / LINE / Directions bar. Appears once the hero has mostly scrolled away. While hidden it is `inert`, so it can't be tabbed into. It sits above the iPhone home bar (`env(safe-area-inset-bottom)`). |
| Menu tabs | The WAI-ARIA tabs pattern: Left/Right arrows, Home and End keys, only the active tab in the Tab order ("roving tabindex"). The underline is one bar moved and stretched with `translateX` + `scaleX` to fit the active tab. |
| Lightbox | Uses the native `<dialog>` element, which gives focus trapping, the Esc key and the dimmed backdrop for free. Arrow keys and swipe change photos; focus returns to the photo you opened. |
| Reviews carousel | A CSS scroll-snap row (works by touch with no JS). JS adds the arrows and dots and tracks which slides are visible. |
| Reduced motion | If the phone's "reduce motion" setting is on, `@media (prefers-reduced-motion: reduce)` and a JS check switch off parallax, reveals and smooth scrolling. Everything is simply shown. |

## 6. Speed: how it scores 100 on Lighthouse

- **No frameworks.** All our own JS and CSS together is about 35 KB gzipped, with no third-party scripts.
- **Content is in the HTML** (baked), so the first paint doesn't wait for JavaScript.
- **Images:** AVIF (smallest) with WebP fallback, via `<picture>`. `srcset` + `sizes` let the
  phone pick the smallest file that looks sharp. Phones get a **separate tall 9:16 hero crop**, so
  they don't download a wide desktop photo and throw most of it away. Below-the-fold images use
  `loading="lazy"`.
- **No layout shift:** every image has `width` and `height`, so its space is reserved before it
  loads. A tiny blurred version of each photo (LQIP, "low-quality image placeholder") shows
  meanwhile.
- **Fonts:** subset to only the characters used (about 24–30 KB each), preloaded, with
  `font-display: swap` so text shows at once in a fallback font.
- **Caching:** files with a content hash in the name (photos, fonts) are cached for a year as
  "immutable". If a photo changes, its name changes, so there's never a stale image. HTML, CSS and
  JS are revalidated on every visit, so updates show up straight away.
- **Lazy extras:** the QR library loads only near the contact section, and the map only on tap.

Note: Lighthouse reports the LCP ("largest contentful paint") element as the header text, not
the hero photo. Chrome ignores images that cover the whole screen, because it treats them as
backgrounds. The hero is preloaded anyway, so it still appears fast.

## 7. Security and privacy

**No trackers, no forms, no cookies, no data collected.** The only thing stored is the language
choice, in the visitor's own browser.

`netlify.toml` sends a strict **Content-Security-Policy (CSP)**. It is a list of rules the browser
enforces: "only run scripts, styles, fonts and images from this site itself; only allow iframes
from OpenStreetMap/Google Maps; never let other sites put this page in a frame." Even if someone
managed to inject HTML, the browser would refuse to run it.

That's why the code follows a few rules:
- **No inline `<script>` or `style="…"` in the HTML.** Theme colors go in `shop.generated.css`.
  The bake checks for inline code and warns.
- Values that JS must set (such as the parallax offset) use `element.style.setProperty()`, which the CSP
  allows, unlike HTML style attributes.
- The JSON-LD block (`<script type="application/ld+json">`) is allowed because it is data, not
  code. The browser never runs it.

Other headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`,
`Permissions-Policy` (camera, mic and location off), and HSTS (always use HTTPS).

## 8. Fonts

- **Noto Serif Thai** (headings) and **IBM Plex Sans Thai** (body), both under the Open Font
  License, which allows self-hosting and subsetting.
- The serif is a **variable font**: one 30 KB file covers every weight from 400 to 700.
- The fonts were **subset** to Thai, basic Latin and a few symbols with
  [fontTools](https://github.com/fonttools/fonttools) (`pip install fonttools brotli`):

```bash
fonttools varLib.instancer NotoSerifThai-VF.ttf wdth=100 wght=400:700 -o NotoSerifThai-inst.ttf
U="U+0020-007E,U+00A0,U+00A9,U+00B7,U+00D7,U+00E9,U+0E01-0E5B,U+200B,U+2009,U+2010-2027,U+2039-203A,U+2190-2193,U+2212,U+25CC"
pyftsubset NotoSerifThai-inst.ttf --unicodes="$U" --layout-features='*' --flavor=woff2 \
  --output-file=site/assets/fonts/noto-serif-thai-var.woff2
pyftsubset IBMPlexSansThai-Regular.ttf --unicodes="$U" --layout-features='*' --flavor=woff2 \
  --output-file=site/assets/fonts/ibm-plex-sans-thai-400.woff2   # same for Medium (500), SemiBold (600)
```

`--layout-features='*'` keeps the OpenType rules that place Thai tone marks correctly. If a shop
needs other characters (e.g. Japanese menu names or `€`), add their ranges to `U` and re-run.

## 9. Files in `tools/` (your computer only, never deployed)

| File | What it does |
| --- | --- |
| `images.py` | Reads `config.photos`, opens each photo in `images-src/`, applies one gentle color grade so all photos match, and saves AVIF + WebP at several widths plus JPEG fallbacks. Also makes the phone hero crop (using the `focus` point), the blurred placeholders, the 1200×630 link-preview image, the paper-grain texture and the favicons. Writes `assets/img/manifest.js`. |
| `bake.mjs` | Loads `config.js` and the templates into a **sandbox** (Node's `vm` module, which gives them a fake `window`), fills every `<!--render:…-->` slot in `index.html`, writes `shop.generated.css`, `404.html`, the manifest, `robots.txt` and `sitemap.xml`. Then prints a "Please check" list (missing alt text, demo notice still on, inline code that the CSP would block…). |
| `serve.mjs` | A small local web server. It reads `netlify.toml` and sends the same headers, so CSP problems show up on your computer before they show up live. |
| `tests/hours.test.mjs` | Unit tests for opening hours (overnight, split days, holidays, closing soon). |
| `tests/interactions.mjs` | Opens the site in real Chrome (Playwright) and clicks through everything: 77 checks, from the language toggle being remembered to the lightbox swipe. |
| `tests/screens.mjs` | Full-page screenshots at 360 / 390 / 768 / 1440 px wide, in either language, optionally with reduced motion. |
| `tests/contrast.mjs` | Checks every text/background color pair in every theme meets WCAG AA (4.5:1). |
| `tests/audit.mjs` | Runs Lighthouse 3 times (mobile, simulated 4G) and reports the median, then runs the axe-core accessibility checker in both languages at phone and desktop width. |
| `tests/_browser.mjs` | Shared helper that starts your installed Chrome for the tests. |

## 10. Accessibility checklist (what was done)

- Landmarks: `<header>`, `<nav>`, `<main>`, `<footer>`, and each section labelled by its heading.
- "Skip to content" link as the first thing you can Tab to.
- Visible focus ring on every interactive element (`:focus-visible`).
- All text at least 4.5:1 contrast in all three themes (tested).
- Every photo has real alt text in both languages. Decorative images have `alt=""`.
- Tabs, lightbox, carousel and mobile menu work by keyboard alone.
- `lang` is correct on the page and on every Thai/English span.
- Buttons are thumb-sized: most are 44 × 44 px, and the TH/EN switch is 44 × 36, well above
  WCAG 2.2's 24 × 24 px minimum target size.
- Reduced motion is respected.

## 11. Interview talking points

- **"Why no React?"** A one-page shop site has almost no state. Vanilla JS keeps the download small
  and has no dependencies to update or break. I still kept things organised: templates (render.js) are
  separate from behaviour (main.js) and logic (hours.js).
- **"How do you avoid duplicate code between server and browser?"** The same template file runs in
  Node (bake) and in the browser (live preview), and a content hash detects when they differ.
- **"How did you make it fast?"** Baked HTML, AVIF and `srcset`, a separate phone hero crop,
  subset fonts, lazy map and QR, and animating only `transform`/`opacity`. Measured with Lighthouse:
  100 in all four categories on mobile.
- **"How is it secure if it's static?"** A strict CSP and security headers, with no inline code,
  no third-party scripts and no forms. Even an injected script wouldn't run.
- **"What was hard?"** Thai typography (tone marks clipping, different line heights) and
  time-zone-correct opening hours with overnight ranges. Both have tests or checks.
- **"What would you add next?"** A small form-free way to update the menu (for example from a Google
  Sheet at bake time), and automated visual regression tests that compare screenshots.
